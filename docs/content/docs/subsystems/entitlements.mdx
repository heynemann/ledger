---
title: Entitlement Checking
description: How Entitled answers "can this tenant use this feature?", what it caches, and the reasons it gives.
---

`Entitled` is the check you put on the request path. It reads the tenant and app from the context, finds the tenant's active subscription, looks up the feature in the plan, and compares usage with the limit.

```go
ctx = context.WithValue(ctx, "tenant_id", "acme")
ctx = context.WithValue(ctx, "app_id", "my-app")

res, err := engine.Entitled(ctx, "api_calls")
if err != nil {
	return err // a store failure
}
if !res.Allowed {
	return tooManyRequests(res.Reason)
}
```

A denial isn't an error. `err` is non-nil only when the store fails while counting usage.

## The result

```go
type Result struct {
	Allowed   bool
	Feature   string
	Used      int64
	Limit     int64
	Remaining int64
	SoftLimit bool
	Reason    string
}
```

`Remaining` is `Limit - Used`, never below zero, and `-1` when the limit is unlimited. `engine.Remaining(ctx, key)` is a shortcut that runs `Entitled` and returns only that number.

## How the answer is worked out

1. No tenant or no app in the context: not allowed, reason `"missing tenant or app context"`.
2. A cached answer for this tenant, app and feature: returned as is.
3. No `active` or `trialing` subscription for the tenant in the app: not allowed, `"no active subscription"`.
4. The subscription's plan is gone: not allowed, `"plan not found"`.
5. The feature isn't in the plan: not allowed, `"feature not in plan"`.
6. A boolean feature: allowed when its `Limit` is above zero. No usage is read.
7. A metered or seat feature: usage is summed over the feature's quota window, then:
   - `Limit` is `-1`: allowed, `Remaining` is `-1`.
   - usage is below `Limit`: allowed.
   - usage is at or past `Limit` and `SoftLimit` is set: allowed, `"over soft limit"`.
   - otherwise: not allowed, `"quota exceeded"`.

Steps 3 to 5 aren't cached, so a tenant who subscribes is entitled on the next check. Boolean, metered and seat answers are cached.

The quota window is the feature's `Period`: the current UTC calendar month for `plan.PeriodMonthly`, the calendar year for `plan.PeriodYearly`, and all time for `plan.PeriodNone` or an empty period. It doesn't follow the subscription's billing period.

Seat features are checked like metered ones, against usage events recorded under the seat key. The seat count on the subscription (`Quantity`) is what invoices bill, and the check doesn't read it. If you gate seats, either `Meter` a seat when you add one (with a negative quantity when you remove one) and give the feature `Period: plan.PeriodNone`, or compare `Quantity` with the limit in your own code.

## Hard and soft limits

A hard limit (the default) denies once usage reaches the limit. A soft limit keeps allowing and sets `Reason` to `"over soft limit"`, so you can warn the tenant while the invoice bills the extra through the feature's tiers.

Ledger doesn't stop a request for you, and it doesn't stop usage from being metered past a hard limit. If you call `Meter` without checking `Allowed`, the usage is recorded and billed.

## Caching

Answers are cached in the store, keyed by tenant, app and feature, for the TTL you set with `ledger.WithEntitlementCacheTTL` (30 seconds by default). The PostgreSQL and SQLite stores keep them in the `ledger_entitlement_cache` table, MongoDB in a collection, and the memory store in a map. So a cache hit is a store read: fast against the memory store, a query against a database.

The engine clears a tenant's cached answers when a subscription is created, changes plan, is paused, resumed or canceled, or is moved by the lifecycle clock. Metering doesn't clear them, so an answer can lag new usage by the TTL plus the meter flush interval. With a hard limit, a tenant can go somewhat past the limit inside that window. Shorten the TTL if that matters more to you than the extra store reads.

To clear answers yourself:

```go
s := engine.Store()
_ = s.Invalidate(ctx, "acme", "my-app")                     // every feature
_ = s.InvalidateFeature(ctx, "acme", "my-app", "api_calls") // one feature
```

## Inspecting a tenant

`InspectEntitlement` answers the same question for a tenant and app you name, straight from the store. It skips the cache and fires no hooks, which makes it the one to use in admin tools:

```go
res, err := engine.InspectEntitlement(ctx, "acme", "my-app", "api_calls")
```

## Hooks

| Hook | Fires when |
|------|------------|
| `OnEntitlementChecked` | A metered or seat answer is computed (not on a cache hit, and not for boolean features) |
| `OnQuotaExceeded` | A computed answer is `"quota exceeded"` |

`OnSoftLimitReached` is declared in the plugin package but never fires.

## Remote access

Ledger has no HTTP routes for entitlements. The Forge dashboard uses the contract intents `entitlements.check` and `entitlements.invalidate`. See [HTTP API](/docs/api-reference/http-api).
