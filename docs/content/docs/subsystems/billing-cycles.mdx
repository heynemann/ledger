---
title: Billing Cycles
description: How periods are worked out, what the lifecycle clock does on each run, and how to bill the periods it ends.
---

Each subscription has one current period, `CurrentPeriodStart` to `CurrentPeriodEnd`. The lifecycle clock moves it forward when it ends. Billing the period that ended is a separate step you take, because Ledger never generates an invoice by itself.

## Period length

The plan's `Pricing.BillingPeriod` sets the length:

| `BillingPeriod` | Period |
|-----------------|--------|
| `plan.PeriodMonthly`, or empty, or no pricing | one calendar month |
| `plan.PeriodYearly` | twelve calendar months |
| `plan.PeriodNone` | a first period of one month, which never rolls |

There are no daily, weekly or quarterly periods.

A period ends on the same day of the month it started, at the same time of day, in UTC. When that day doesn't exist, the period ends on the month's last day, and the next one goes back to the original day: a subscription that started on 31 January ends its periods on 28 (or 29) February, then 31 March.

```
created 2026-01-31 10:00 UTC, monthly
  period 1: 2026-01-31 10:00 → 2026-02-28 10:00
  period 2: 2026-02-28 10:00 → 2026-03-31 10:00
  period 3: 2026-03-31 10:00 → 2026-04-30 10:00
```

## The lifecycle clock

`Start` runs `Advance(ctx, now)` every minute (`ledger.WithLifecycleInterval` changes that, and `0` turns it off). One run does four steps, in this order:

| Step | Method | What it does | Hook |
|------|--------|--------------|------|
| 1 | `AdvancePeriods` | Moves every `active`, `trialing` or `past_due` subscription whose period has ended into the period that contains now, in one write however many periods it missed. It never moves past a scheduled cancel. | `OnSubscriptionRenewed`, once per subscription, listing every period that ended |
| 2 | `EnactCancels` | Cancels every subscription whose `CancelAt` has passed, paused ones included, and sets `CanceledAt` to `CancelAt`. | `OnSubscriptionCanceled` |
| 3 | `EndTrials` | Makes every `trialing` subscription whose `TrialEnd` has passed `active`. A paused subscription's trial is left alone. | `OnSubscriptionTrialEnded` |
| 4 | `MarkInvoicesPastDue` | Moves every `pending` invoice whose due date has passed to `past_due`. The subscription isn't touched. | `OnInvoicePastDue` |

`Advance` returns a `LifecycleReport` with the IDs each step changed. Each step keeps going past a row that fails, and the errors come back joined.

Every change is a conditional store write, so the clock is safe to run on several replicas at once. Only the replica whose write lands reports the change and fires its hook. A paused subscription doesn't roll: its period stands still until `ResumeSubscription` stretches it by the length of the pause.

### Running it yourself

Turn the background clock off and call `Advance` from your own scheduler, or from a test with any time you like:

```go
engine := ledger.New(store, ledger.WithLifecycleInterval(0))
// ...
report, err := engine.Advance(ctx, time.Now())
if err != nil {
	log.Println("lifecycle:", err)
}
if !report.Empty() {
	log.Println("advanced", len(report.PeriodsAdvanced), "past due", len(report.InvoicesPastDue))
}
```

Each step is also a method of its own (`AdvancePeriods`, `EnactCancels`, `EndTrials`, `MarkInvoicesPastDue`) if you want to run them on different schedules. In the Forge extension, set `disable_lifecycle: true`.

## Billing ended periods

`OnSubscriptionRenewed` receives a `*subscription.Renewal`: the subscription as stored after the move, and `Ended`, every period that ended in it. Generate an invoice for each with `ForPeriod`:

```go
type biller struct{ engine *ledger.Ledger }

func (b *biller) Name() string { return "biller" }

func (b *biller) OnSubscriptionRenewed(ctx context.Context, renewal interface{}) error {
	r, ok := renewal.(*subscription.Renewal)
	if !ok {
		return nil
	}
	for _, p := range r.Ended {
		inv, err := b.engine.GenerateInvoice(ctx, r.Subscription.ID, ledger.ForPeriod(p.Start, p.End))
		if errors.Is(err, ledger.ErrAlreadyExists) {
			continue // billed already
		}
		if err != nil {
			return err
		}
		if err := b.engine.FinalizeInvoice(ctx, inv.ID); err != nil {
			return err
		}
	}
	return nil
}
```

The plugin needs the engine, and the engine needs the plugin at construction, so register it with a pointer you fill in afterwards:

```go
b := &biller{}
engine := ledger.New(store, ledger.WithPlugin(b))
b.engine = engine
```

Hook delivery is at most once and in-process. If the process dies between the period write and the hook, or the hook returns an error, that announcement is gone: the clock never fires it again. So run a reconciliation now and then: list subscriptions, and for every period that ended without an invoice, call `GenerateInvoice` with `ForPeriod`. `ErrAlreadyExists` marks the ones already billed.

`ForPeriod` only accepts the current period or earlier ones on the subscription's cadence, so a reconciliation can't invent periods. A period from before an older pause, which Ledger no longer remembers, is refused.

## What a renewal doesn't do

- It doesn't generate, finalize or collect an invoice.
- It doesn't prorate. A plan change takes effect for the whole period the next invoice bills.
- It doesn't reset quotas. Quota windows follow the calendar, not the period. See [Entitlements](/docs/subsystems/entitlements).
- It doesn't move a subscription to `past_due` or `expired`, whatever its invoices look like.
