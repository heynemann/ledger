---
title: Usage Metering
description: How Meter records usage, how the flush worker writes it, and how quota checks and invoices count it.
---

You record usage with one call after the work is done:

```go
if err := engine.Meter(ctx, "api_calls", 1); err != nil {
	// ErrInvalidInput: no tenant or app in ctx
	// ErrMeterBufferFull: the buffer is full; retry or shed load
}
```

`Meter` reads the tenant and app from the context values `"tenant_id"` and `"app_id"`, builds a `meter.UsageEvent` with a new `uevt_` ID and the current UTC time, and puts it on a buffered channel. It doesn't touch the store, so it returns in microseconds and never waits on the database.

It doesn't check the feature key against any plan, and it accepts any quantity, negative ones included. A negative quantity works as a correction, but a period whose usage totals below zero fails `GenerateInvoice`.

## The flush worker

```
Meter() ──> channel (10,000 events)
                 │
                 v
           flush worker ── batch reaches batch size ──┐
                 │                                    ├──> store.IngestBatch
                 └──────── flush interval ticks ──────┘
```

`Start` launches one worker that collects events into a batch and writes it with `store.IngestBatch` when the batch reaches the batch size or when the flush interval ticks, whichever comes first. Both default to 100 events and 5 seconds:

```go
engine := ledger.New(store, ledger.WithMeterConfig(500, 2*time.Second))
```

What follows from that design:

- Usage counts toward quota checks and invoices only after its batch is written. Under light traffic that's up to one flush interval later.
- The channel holds 10,000 events, and the size isn't configurable. When it's full, `Meter` returns `ErrMeterBufferFull` (which `ledger.IsRetryable` reports as retryable) and drops the event.
- A batch that fails to write is logged at error level and dropped. There's no retry.
- On `Stop`, the worker writes the batch it holds and exits. Events still waiting in the channel at that moment can be lost, so stop taking traffic before you call `Stop`.
- `OnUsageFlushed(ctx, count, elapsed)` fires after each successful write. `OnUsageIngested` is declared in the plugin package but never fires.

## The usage event

```go
type UsageEvent struct {
	ID             id.UsageEventID
	TenantID       string
	AppID          string
	FeatureKey     string
	Quantity       int64
	Timestamp      time.Time
	IdempotencyKey string
	Metadata       map[string]string
}
```

`Meter` leaves `IdempotencyKey` and `Metadata` empty. The stores skip an event whose non-empty `IdempotencyKey` they've already stored, so if you need idempotent ingestion (replaying a queue, importing from another system) write the events yourself:

```go
err := engine.Store().IngestBatch(ctx, []*meter.UsageEvent{{
	ID:             id.NewUsageEventID(),
	TenantID:       "acme",
	AppID:          "my-app",
	FeatureKey:     "api_calls",
	Quantity:       250,
	Timestamp:      time.Now().UTC(),
	IdempotencyKey: "import-2026-10-14-acme",
}})
```

## How usage is counted

Quota checks and invoices count the same events over different windows.

A quota check (`Entitled`, `Remaining`) sums the events for the tenant, app and feature since the start of the feature's `Period`: the current UTC calendar month for `plan.PeriodMonthly`, the calendar year for `plan.PeriodYearly`, and all time for `plan.PeriodNone` or an empty period. The window comes from the wall clock.

An invoice sums the events inside the period it bills, from the period's start to its end, or to now while the period is still running. Two invoices for back-to-back periods never count the same event. A feature can name a usage aggregator plugin in its `Metadata` under `"aggregator"` to total its events some other way, such as a maximum instead of a sum. See [Custom plugin](/docs/guides/custom-plugin#usageaggregator).

So a subscription that renews on the 15th is billed for the 15th to the 15th, while its monthly quota resets on the 1st.

## Querying usage

The engine has no query methods of its own for usage. Go through the store:

```go
s := engine.Store()

// Total for a feature in its quota window.
used, err := s.Aggregate(ctx, "acme", "my-app", "api_calls", plan.PeriodMonthly)

// Several features at once.
totals, err := s.AggregateMulti(ctx, "acme", "my-app", []string{"api_calls", "exports"}, plan.PeriodMonthly)

// The events themselves, in [Start, End).
events, err := s.QueryUsage(ctx, "acme", "my-app", meter.QueryOpts{
	FeatureKey: "api_calls",
	Start:      time.Date(2026, 10, 1, 0, 0, 0, 0, time.UTC),
	End:        time.Date(2026, 11, 1, 0, 0, 0, 0, time.UTC),
	Limit:      100,
})

// Delete events older than a cutoff. Returns how many were removed.
removed, err := s.PurgeUsage(ctx, time.Now().AddDate(-1, 0, 0))
```

Nothing purges usage automatically. Keep events at least as long as you might bill a past period with `ForPeriod`.

## Tuning

- Raise the batch size to cut store writes under heavy traffic. The buffer stays at 10,000, so a slow store fills it sooner when batches are large and writes are slow.
- Lower the flush interval when quota checks need to see usage sooner. The entitlement cache TTL adds its own delay on top.
- In tests, use a short flush interval and wait for it, or write events with `IngestBatch` and skip the buffer.

## Remote access

Ledger has no HTTP routes for metering. The Forge dashboard reads usage through the contract intents `usage.events` and `usage.aggregate`, and records none. See [HTTP API](/docs/api-reference/http-api).
