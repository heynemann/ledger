---
title: Multi-Tenancy
description: What the tenant and app identifiers scope, where Ledger reads them, and what you have to check yourself.
---

Ledger scopes its data with two strings. You choose both, and Ledger never generates them.

- `TenantID` is the customer you bill: an organization, a workspace, a user. Subscriptions, usage events and invoices carry it.
- `AppID` is the product or deployment the billing belongs to. Plans, catalog features, coupons, subscriptions, usage events and invoices carry it.

A plan isn't owned by a tenant. You create plans for an app, and tenants subscribe to them.

| Entity | `TenantID` | `AppID` | Unique within the app |
|--------|:---:|:---:|---|
| `plan.Plan` | | yes | `Slug` |
| `feature.Feature` (catalog) | | yes, or empty for a global feature | `Key` |
| `coupon.Coupon` | | yes | `Code` |
| `subscription.Subscription` | yes | yes | |
| `meter.UsageEvent` | yes | yes | |
| `invoice.Invoice` | yes | yes | |

## Where Ledger reads them from the context

Only three methods read the tenant and app from the context: `Entitled`, `Remaining` and `Meter`. They look for the values under the plain string keys `"tenant_id"` and `"app_id"`:

```go
ctx = context.WithValue(ctx, "tenant_id", "acme")
ctx = context.WithValue(ctx, "app_id", "my-app")

res, err := engine.Entitled(ctx, "api_calls")
```

There are no helper functions for this, and the keys have to be untyped strings. A linter will likely warn about a string context key; that's the key the engine reads, so silence the warning where you set it. If either value is missing or isn't a string, `Meter` returns `ledger.ErrInvalidInput` and `Entitled` returns a result with `Allowed: false` and the reason `"missing tenant or app context"`.

`InspectEntitlement(ctx, tenantID, appID, key)` takes both as arguments instead, skips the cache and fires no hooks. It's for an operator looking at a customer, not for enforcement.

## Everything else takes IDs, and doesn't check the tenant

The rest of the engine works by entity ID: `GetSubscription(ctx, subID)`, `GenerateInvoice(ctx, subID)`, `ApplyCoupon(ctx, subID, code)` and so on. None of them compares the entity's tenant or app with anything in the context. If a request names a subscription or an invoice, check that it belongs to the caller before you act on it:

```go
sub, err := engine.GetSubscription(ctx, subID)
if err != nil {
	return err
}
if sub.TenantID != callerTenant || sub.AppID != callerApp {
	return ledger.ErrNotFound
}
```

A few rules the engine does enforce:

- `CreateSubscription` refuses a subscription with no `TenantID`, with an error wrapping `ErrInvalidInput`. Every store reads an empty tenant as "every tenant", so a subscription without one would later be billed for other customers' usage.
- A subscription's plan must be in the same app (`plan.AppID == sub.AppID`) and active. `ChangePlan` applies the same rule to the new plan.
- `GenerateInvoice` refuses a subscription with no tenant.
- `ApplyCoupon` looks the code up in the subscription's app.
- `UpdatePlan` refuses to move a plan to another app.

## Listing across tenants

The store's list methods take the tenant and app as arguments, and an empty tenant means every tenant in that app. `ListSubscriptions(ctx, "", "my-app", opts)` lists every subscription in `my-app`. That's how `DeletePlan` checks whether any subscription still uses a plan, and it's useful for your own billing runs. Go through `engine.Store()` to reach them.

`GetActiveSubscription(ctx, tenantID, appID)` returns the tenant's newest subscription in that app whose status is `active` or `trialing`, or `ErrNoActiveSubscription`. A tenant can hold more than one live subscription in an app; quota checks always use the newest.

## Global catalog features

A catalog feature with an empty `AppID` is global. `ListGlobalFeatures` returns those, and `ListFeatures(ctx, appID, opts)` returns one app's. A plan feature can point at a catalog feature through `CatalogID`, but quota checks and invoices read only the plan's own `Features` list.

## In the database

The SQL stores keep `tenant_id` and `app_id` as ordinary columns with composite indexes that lead with `(tenant_id, app_id)` on subscriptions, invoices and usage events, and unique indexes on `(slug, app_id)` for plans, `(code, app_id)` for coupons and `(key, app_id)` for catalog features. There's no row-level security, and queries filter by whatever tenant and app the engine passes them.

## In the Forge dashboard

The dashboard contract contributor treats the app as the security boundary. An operator sees every tenant in one app: the `app_id` claim on their principal, or the extension's configured `app_id` when the claim is missing. With `require_app_claim: true`, a request without the claim is refused. Nothing in a request body can pick a different app. See [Forge extension](/docs/guides/forge-extension#dashboard-contributor).
