---
title: HTTP API
description: Ledger serves no REST API. This page covers what exists instead, the Forge dashboard contract, and how to expose billing over HTTP yourself.
---

Ledger has no HTTP routes. The engine is a Go library, and the Forge extension registers no handlers either. There are no `/ledger/...` or `/webhooks/...` endpoints, no request or response formats, and no HTTP status mapping.

The extension's config does have `base_path` and `disable_routes` keys, with `WithBasePath` and `WithDisableRoutes` options. They're read and logged, and do nothing else.

What does exist:

- The Go API, documented in [Go packages](/docs/api-reference/go-packages).
- The Forge dashboard contract, described below, which the dashboard uses to manage billing.
- Whatever endpoints you write yourself around the engine.

## The Forge dashboard contract

When your Forge app runs both the Ledger extension and the Forge dashboard extension, the dashboard calls the Ledger extension's `RegisterContractContributor` during its own start. Ledger registers a contributor named `ledger` with two capabilities, `ledger.read` for queries and `ledger.write` for commands.

The dashboard serves every contributor's intents itself. In Forge v1.12.7 that's a `POST` of a contract envelope to `<dashboard base>/api/dashboard/v1`; the Forge dashboard docs describe the envelope, authentication, CSRF and idempotency. The React pages that call Ledger's intents live in forge-dashboard's `plugin-ledger` package.

Every request is scoped to one app: the `app_id` claim on the caller's principal, or the extension's `app_id` setting when the claim is missing. With `require_app_claim: true`, a request without the claim is refused with `PERMISSION_DENIED`. A request can't name a different app, and an entity from another app reads as not found.

### Intents

| Intent | Kind | What it does |
|--------|------|--------------|
| `plans.list`, `plans.detail` | query | Lists or reads plans in the app |
| `plans.create`, `plans.update` | command | `CreatePlan`, `UpdatePlan` |
| `plans.activate`, `plans.archive`, `plans.delete` | command | `ActivatePlan`, `ArchivePlan`, `DeletePlan` |
| `plans.syncToProvider`, `plans.importFromProvider` | command | `SyncPlanToProvider`, `ImportPlanFromProvider` |
| `features.list`, `features.detail` | query | Lists or reads catalog features, the app's and global ones |
| `features.create`, `features.update`, `features.archive`, `features.delete` | command | The catalog feature methods |
| `features.syncToProvider`, `features.importFromProvider` | command | `SyncFeatureToProvider`, `ImportFeatureFromProvider` |
| `subscriptions.list`, `subscriptions.detail`, `subscriptions.usage` | query | Lists or reads subscriptions, and a subscription's usage against its plan |
| `subscriptions.create`, `subscriptions.changePlan` | command | `CreateSubscription`, `ChangePlan` |
| `subscriptions.pause`, `subscriptions.resume`, `subscriptions.cancel` | command | `PauseSubscription`, `ResumeSubscription`, `CancelSubscription` |
| `subscriptions.syncToProvider`, `subscriptions.importFromProvider` | command | `SyncSubscriptionToProvider`, `ImportSubscriptionFromProvider` |
| `invoices.list`, `invoices.detail`, `invoices.pending` | query | Lists or reads invoices |
| `invoices.export` | query | `ExportInvoice` through a registered formatter |
| `invoices.generate`, `invoices.finalize`, `invoices.markPaid`, `invoices.void` | command | `GenerateInvoice`, `FinalizeInvoice`, `MarkInvoicePaid`, `MarkInvoiceVoided` |
| `invoices.syncToProvider`, `invoices.importFromProvider` | command | `SyncInvoiceToProvider`, `ImportInvoiceFromProvider` |
| `coupons.list`, `coupons.detail` | query | Lists or reads coupons |
| `coupons.create`, `coupons.update`, `coupons.delete`, `coupons.apply` | command | `CreateCoupon`, `UpdateCoupon`, `DeleteCoupon`, `ApplyCoupon` |
| `usage.events`, `usage.aggregate` | query | Reads usage events and totals from the store |
| `entitlements.check` | query | `InspectEntitlement`: a fresh answer for a named tenant, without the cache |
| `entitlements.invalidate` | command | Clears a tenant's cached quota answers |
| `paymentMethods.list` | query | `ListPaymentMethods` |
| `overview.stats`, `overview.recentInvoices` | query | Counts and recent invoices for the dashboard's overview |
| `settings.detail` | query | The extension's meter, cache and lifecycle settings |

The full list, with each command's cache invalidations, is in `extension/contract/manifest.yaml`. The input and output types are the exported structs in `extension/contract` (`PlanCreateInput`, `SubscriptionDetail` and so on).

There's no intent for `Meter` or `Entitled`. Usage is recorded by your own code, never through the dashboard.

## Exposing billing over HTTP yourself

Put the engine behind your own handlers. A quota-gated endpoint looks like this with the standard library:

```go
mux.HandleFunc("GET /reports", func(w http.ResponseWriter, r *http.Request) {
	tenant := tenantFromAuth(r) // your auth
	ctx := context.WithValue(r.Context(), "tenant_id", tenant)
	ctx = context.WithValue(ctx, "app_id", "my-app")

	res, err := engine.Entitled(ctx, "reports")
	if err != nil {
		http.Error(w, "billing unavailable", http.StatusServiceUnavailable)
		return
	}
	if !res.Allowed {
		http.Error(w, res.Reason, http.StatusTooManyRequests)
		return
	}

	// ... build the report ...

	if err := engine.Meter(ctx, "reports", 1); err != nil {
		log.Println("meter:", err)
	}
})
```

For a payment provider's webhooks, see [Serving webhooks](/docs/subsystems/payments#serving-webhooks). Anything that takes an entity ID from a request (an invoice to show, a subscription to cancel) must check that the entity's `TenantID` and `AppID` belong to the caller, because the engine doesn't. See [Multi-tenancy](/docs/concepts/multi-tenancy).
